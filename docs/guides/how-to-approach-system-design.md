# 系统设计答题法

系统设计面试最怕的不是“不会画图”，而是一上来就开始堆组件。真正稳定的答题方式应该像教程一样有固定章节。

## 推荐答题顺序

### Step 1. 先澄清需求

先确认：

- 这是核心功能还是 MVP
- 读多写少还是写多读少
- 实时性要求多高
- 是否有多租户、多地域、强一致要求

如果需求没澄清，后面所有设计都可能是错题。

### Step 2. 做粗粒度容量估算

最低要讲：

- QPS / 峰值流量
- 数据规模
- 存储量级
- 带宽量级

估算不要求绝对精确，但它决定你后面为什么要引入缓存、分片、异步化和限流。

### Step 3. 画高层架构

这一步只讲核心组件，不要细节过早下沉：

- 接入层
- 核心服务层
- 存储层
- 缓存 / MQ / 搜索 / 离线链路

目标是先建立面试官和你的共同上下文。

### Step 4. 讲核心链路

选最重要的一条链路讲透，比如：

- 下单链路
- 发帖到分发链路
- 写入到读取链路
- 请求到结果返回链路

一条链路里至少讲清：

- 请求怎么进来
- 数据怎么落
- 为什么要异步
- 一致性怎么处理

### Step 5. 讲瓶颈和 trade-off

这是系统设计题拉开差距的地方。必须讲：

- 哪些地方会成为热点
- 为什么引入缓存/MQ/分片
- 这么做换来了什么
- 又失去了什么

面试不是让你把架构堆满，而是让你讲清楚为什么这么取舍。

### Step 6. 讲扩展性和故障处理

至少补这些点：

- 单点故障怎么办
- 积压怎么办
- 热点怎么办
- 限流和降级怎么做
- 数据一致性失败如何补偿

### Step 7. 收束总结

最后用 20-30 秒把关键选择再说一遍：

- 为什么是这个架构
- 最大瓶颈是什么
- 如果继续扩容，下一步怎么演进

## 面试中最常见的错误

- 一上来直接画图，不问需求
- 完全不做估算
- 遇到问题只会说“加 Redis / 上 MQ”
- 只讲 happy path，不讲失败场景
- 讲了很多组件，但说不出 trade-off

## 你至少要练到什么程度

- 能在 `2 分钟` 内讲出答题框架
- 能在 `5-8 分钟` 内讲完 1 道中型题
- 能在追问时补充一致性、容量和故障处理
