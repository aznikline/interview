# 消息队列、消费模型与序列化

## 1 分钟速答

消息系统设计题真正考的是：`消息怎么分发`、`消费位点怎么管理`、`顺序和吞吐如何取舍`、`消息格式怎么兼容演进`。如果只会回答“用 MQ 削峰解耦”，基本停留在初级层面。

## 核心机制

### push vs pull

这是最常见的基础追问之一。

- `push`：低延迟，但服务端压力更大
- `pull`：消费者更自主，更容易做速率控制和批量消费

大多数成熟 MQ 系统更偏 pull，不是因为“设计喜欢”，而是因为它更利于消费端自治和扩展。

### offset 与消费组

消息系统一旦进入工程语境，就离不开：

- offset 怎么提交
- 消费组如何扩容
- 重平衡时会不会重复消费

这类问题直接关系到“至少一次”和顺序性的代价。

### 顺序、重试和死信

顺序消息通常意味着：

- 分区粒度更细
- 并行度受限
- 重试和阻塞更麻烦

死信队列不是“异常垃圾桶”，而是为了把不可立即恢复的消息从主链路剥离出去。

### 序列化与兼容性

这部分常被忽略，但非常能体现工程深度：

- 为什么要选 protobuf / avro / json
- schema 变更如何兼容老消费者
- 序列化大小、解析速度、可读性之间如何取舍

## 高频问法

- push 和 pull 怎么选？
- 为什么 offset 提交时机会影响重复消费？
- 顺序消息为什么会牺牲吞吐？
- 死信队列解决什么问题？
- protobuf 和 JSON 怎么取舍？

## 深挖与误区

- 不要把 MQ 题回答成“削峰解耦”四个字
- 不要忽略消费位点和重平衡
- 不要把序列化格式看成纯技术偏好，它直接影响兼容性和带宽成本
