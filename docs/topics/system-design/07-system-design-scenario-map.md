# 系统设计场景地图

## 1 分钟速答

系统设计题最容易答散，不是因为组件不会，而是因为没有把题目识别成具体场景。短链接、秒杀、Feed、MQ、搜索建议、ID、恢复治理，本质上是在考不同资源瓶颈和不同 trade-off。这份地图就是把这些高频题重新按“场景”组织起来。

## 核心机制

### 为什么系统设计更适合按场景复习

如果只按组件看：

- 容易一直重复“加缓存、加 MQ”
- 不知道每道题真正的瓶颈在哪里
- 一被追问到 trade-off 和故障处理就空

如果按场景看，你会更容易先抓住：

- 这是读多写少，还是写多读少
- 瓶颈在存储、带宽、热点、排序还是一致性
- 它更怕流量洪峰，还是更怕恢复期二次事故

### 场景 1：高频读跳转类

代表题：

- 短链接
- 搜索建议
- 热点配置分发

重点不是“怎么存”，而是：

- 如何低延迟命中
- 如何挡住热点
- 如何做过期和降级

### 场景 2：高并发写入与库存保护

代表题：

- 秒杀系统
- 下单链路
- 抢优惠券 / 抢票

重点不是“上 Redis”四个字，而是：

- 如何削峰
- 如何保护核心资源
- 如何补偿和恢复

### 场景 3：时间线与聚合读取

代表题：

- Feed 流
- 通知中心
- 活动流 / 关注流

重点不是“用什么表”，而是：

- fanout on write 和 fanout on read 怎么取舍
- 热门用户如何特殊处理
- 删除、屏蔽、补偿怎么传播

### 场景 4：异步解耦与事件驱动

代表题：

- 消息队列
- 订单状态流转
- 数据同步与异步通知

重点不是“Broker 怎么存消息”，而是：

- 为什么这条链路适合异步
- 顺序、可用性、吞吐如何取舍
- 积压和恢复怎么处理

### 场景 5：全局标识与路由

代表题：

- 全局唯一 ID
- 短码生成
- 分片路由键设计

重点不是“UUID 还是 Snowflake”的百科，而是：

- 唯一性和有序性怎么平衡
- 时钟回拨和热点分片怎么处理

### 场景 6：检索与索引

代表题：

- 搜索建议
- 搜索结果页
- 倒排索引服务

重点不是“Trie / 倒排”定义，而是：

- 实时更新和查询延迟怎么平衡
- 个性化和热门结果怎么混排
- 风险词、脏词、降级怎么做

### 场景 7：恢复与资源保护

代表题：

- 缓存挂了怎么办
- MQ 恢复后如何放量
- 下游抖动时如何熔断和降级

重点不是“故障发生了”，而是：

- 先保哪条链路
- 恢复时怎么预热和平滑放量
- 哪些指标决定你该不该继续开闸

## 高频问法

- 为什么系统设计题不能只按组件准备？
- 为什么短链接和搜索建议都属于高频读场景，但答法不一样？
- 为什么秒杀和下单链路总会问到补偿和恢复？
- 为什么 Feed 流和消息队列题都容易问 trade-off？
- 为什么恢复治理能直接拉开资深度差距？

## 深挖与误区

- 不要把不同场景都答成“加缓存、加 MQ”
- 不要只会讲 happy path，不讲容量、限流、降级、恢复
- 不要只记案例名，要先识别资源瓶颈和约束
