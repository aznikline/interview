# 搜索、索引与消息系统设计

## 1 分钟速答

搜索和消息系统常被单独问，是因为它们都体现了一类系统设计核心能力：前者强调 `检索与索引结构`，后者强调 `异步解耦与可靠投递`。真正要回答的是为什么选这种结构，以及代价是什么。

## 核心机制

### 搜索与索引

搜索系统最常见的问题不是“用不用 Elasticsearch”，而是：

- 数据怎么建索引
- 实时性要求多高
- 排序和分页怎么做
- 热查询和热点词怎么处理

如果讲搜索建议，还要补：

- prefix / trie / 倒排索引 各适合什么场景
- 实时写入和离线构建怎么平衡

### 消息系统

消息队列设计类题最关键的是：

- push 还是 pull
- offset 怎么管理
- 顺序性怎么保证
- 重试与死信如何处理
- 消费组与扩容怎么设计

很多人只会讲“用 MQ 解耦”，但答不到系统层。

### 共同的 trade-off

这两类系统都绕不开一个问题：

- 更高吞吐通常意味着更复杂的一致性和恢复逻辑
- 更高实时性通常意味着索引或队列系统更难做

## 高频问法

- 搜索建议系统怎么设计？
- 倒排索引为什么适合搜索？
- 消息队列为什么通常选择 pull 模式？
- 顺序消息和吞吐为什么经常冲突？
- 死信队列解决什么问题？

## 深挖与误区

- 不要把搜索题答成“我上 ES”
- 不要把消息题答成“削峰填谷就完了”
- 必须讲清数据结构、消费模型、恢复逻辑和 trade-off
