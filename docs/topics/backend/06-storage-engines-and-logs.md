# 存储引擎、日志与刷盘机制

## 1 分钟速答

数据库内部机制题真正考的不是名词，而是你是否理解 `写入为什么能落盘`、`崩溃后为什么能恢复`、`为什么刷盘策略会影响延迟`。把存储引擎、redo/undo/binlog、checkpoint、fsync 讲清楚，后端深度会明显上一个台阶。

## 核心机制

### 写入链路

一条更新语句进入 MySQL 之后，至少要回答清楚：

- 数据页是否在 buffer pool
- redo log 何时写
- binlog 何时写
- 事务提交时何时真正刷盘

很多人只会背“两阶段提交”，但说不出它想解决什么问题。

### redo / undo / binlog 的边界

- `redo log`：面向物理页修改，解决崩溃恢复
- `undo log`：面向回滚和 MVCC 历史版本
- `binlog`：面向复制和归档

面试里常见失误是把三者混成“都是日志”。

### checkpoint 与刷盘

如果所有脏页都等崩溃时恢复，恢复成本会很高，所以需要 checkpoint。

重点不是背定义，而是理解：

- checkpoint 是控制恢复成本
- 刷盘策略会影响提交延迟
- fsync 太频繁会带来明显性能抖动

### 存储引擎视角

至少要知道 InnoDB 和 MyISAM 的差异为什么重要：

- 事务支持
- 行锁 vs 表锁
- 崩溃恢复
- buffer pool

## 高频问法

- redo / undo / binlog 分别解决什么问题？
- 两阶段提交为什么需要？
- checkpoint 的意义是什么？
- fsync 为什么会影响吞吐和尾延迟？
- InnoDB 为什么更适合事务型系统？

## 深挖与误区

- 不要把“提交成功”简单理解成“数据已经永久写入磁盘”
- 不要把 binlog 当成崩溃恢复主机制
- 不要只讲概念，不讲刷盘频率和性能波动的关系
