# 网络与协议基础

## 1 分钟速答

后端面试里的网络题，不是让你背教科书，而是看你能不能把 `连接建立`、`数据传输`、`超时重试`、`拥塞与流控`、`连接复用` 这些机制解释到真实服务现象上，比如长尾延迟、连接堆积、TIME_WAIT、重试风暴。

## 核心机制

### TCP 为什么仍然是主角

大多数后端服务依然跑在 TCP 之上，因为它提供：

- 有序传输
- 丢包重传
- 流量控制
- 拥塞控制

面试里真正要讲的是这些能力的代价：可靠性来自状态管理、ACK、重传和窗口机制，这些都会影响延迟、吞吐和连接数量。

### 连接管理

最常被问的不是“三次握手背一下”，而是：

- 为什么需要三次握手
- 为什么挥手通常是四次
- TIME_WAIT 为什么会堆积
- CLOSE_WAIT 为什么经常意味着应用代码没关连接

这些问题都和服务端资源管理直接相关。

### 流量控制与拥塞控制

这两者很容易混：

- 流量控制解决“接收方吃不下”
- 拥塞控制解决“网络路径扛不住”

当服务尾延迟高时，既可能是业务处理慢，也可能是网络链路在退让、重传或丢包。

### HTTP 演进

至少要能回答：

- HTTP/1.1 为什么有队头阻塞
- HTTP/2 为什么引入多路复用
- HTTP/3 为什么跑到 QUIC/UDP 上

不要把这类问题回答成“版本更新了所以更快”，要讲清连接复用、头阻塞和状态管理。

## 高频问法

- 三次握手为什么不是两次？
- TIME_WAIT 太多怎么办？
- HTTP/2 为什么比 HTTP/1.1 更适合高并发请求？
- 重试为什么可能把系统打崩？
- 流量控制和拥塞控制有什么区别？

## 深挖与误区

- 不要把网络题回答成纯协议定义
- 不要只会说“长连接更好”，不讲连接池、空闲超时和负载均衡
- 不要把超时重试当成无代价操作，它很容易放大故障
