# 后端场景地图

## 1 分钟速答

后端准备最容易犯的错，是把内容切成 `MySQL / Redis / MQ` 三块分别背。真实面试更像是在问一条业务链路：写请求怎么落库、热点怎么挡、异步怎么解耦、失败怎么补偿、恢复怎么放量。所以后端更适合按“场景”而不是按“组件”去复习。

## 核心机制

### 这份地图在解决什么问题

它把后端高频面试点重组为几条最常见业务场景：

- 写链路与事务
- 缓存与热点治理
- 消息与异步解耦
- 一致性与补偿
- 高并发与流量保护
- ID、锁、幂等与状态流转
- 排障、恢复和复盘

这样你在面试里不会只说“用了 Redis”，而是能说明 Redis 在链路里解决了什么问题、又带来了什么边界。

### 场景 1：写链路与事务

代表问题：

- MySQL 为什么用 B+ 树？
- MVCC 解决了什么？
- redo / undo / binlog 分别负责什么？
- 可重复读为什么还能防幻读？

你真正要讲清的是：

- 一条写请求如何落库
- 数据一致性靠什么保证
- 锁和版本并发各覆盖什么问题

### 场景 2：缓存与热点治理

代表问题：

- Redis 为什么快？
- 缓存穿透、击穿、雪崩怎么治理？
- 为什么通常删缓存而不是更新缓存？
- 热 key、大 key、慢命令怎么排查？

你真正要讲清的是：

- 缓存如何减轻数据库压力
- 缓存本身会制造哪些一致性和热点问题
- 故障时系统如何退化

### 场景 3：消息与异步解耦

代表问题：

- MQ 如何保证消息不丢？
- 至少一次为什么一定带来重复消费？
- 消息积压怎么办？
- 顺序消息和高可用如何取舍？

你真正要讲清的是：

- 哪些链路适合异步
- 消息系统如何换取吞吐和削峰
- 失败时如何重试、隔离和重放

### 场景 4：一致性与补偿

代表问题：

- 为什么很多业务不用强一致事务？
- 2PC、TCC、SAGA、本地消息表怎么选？
- 补偿、幂等、重试、对账分别负责什么？
- 分布式锁为什么经常不是最优解？

你真正要讲清的是：

- 一致性目标到底是什么
- 业务能接受哪种不一致窗口
- 失败后靠什么兜底

### 场景 5：高并发与流量保护

代表问题：

- 如何设计秒杀 / 下单链路？
- 限流、熔断、降级各放在哪层？
- 为什么恢复期也会再次打崩系统？

你真正要讲清的是：

- 如何削峰和保护核心链路
- 哪些功能可以先放弃
- 恢复为什么比故障本身还危险

### 场景 6：ID、锁、幂等与状态流转

代表问题：

- 全局唯一 ID 怎么设计？
- 时钟回拨为什么危险？
- 为什么唯一约束和状态机经常比锁更稳？
- 幂等到底落在哪里？

你真正要讲清的是：

- 如何避免重复写、重复扣减、重复发奖
- 如何让状态流转可观测、可重试、可恢复

### 场景 7：排障、恢复与复盘

代表问题：

- 热 key、慢查询、消息积压、慢请求先看什么？
- 一次事故复盘里最应该补哪层？
- 为什么恢复不能瞬间全量放量？

你真正要讲清的是：

- 看哪些指标
- 先止血还是先扩容
- 这次事故暴露的是架构问题还是治理问题

## 高频问法

- 为什么后端准备更适合按场景而不是按组件？
- 为什么“删缓存”能连到“一致性和恢复”？
- 为什么 MQ 题最终都绕不开幂等和积压？
- 为什么平台岗位更容易追问恢复和复盘？
- 为什么很多事故题本质是资源保护题？

## 深挖与误区

- 不要把后端题答成中间件百科
- 不要只会讲 happy path，忽略失败和恢复
- 不要把锁、幂等、补偿、对账当成彼此替代，它们解决的问题并不一样
