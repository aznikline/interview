# 网络 I/O、epoll 与零拷贝

## 1 分钟速答

网络 I/O 面试的关键不是把 `select / poll / epoll` 定义背出来，而是解释：在高并发服务里，线程为什么会等、数据为什么会拷贝、请求为什么会被慢连接拖住，以及 epoll 和零拷贝分别缓解了什么问题。

## 核心机制

### 阻塞与非阻塞

最基础的问题不是“API 名字”，而是线程在等什么：

- 阻塞 I/O：线程会卡在系统调用上
- 非阻塞 I/O：调用立刻返回，但你需要知道什么时候能继续处理

面试官真正关心的是线程资源如何被占住，以及高并发时这种占用为什么会放大。

### select / poll / epoll

三者常被问，但不要背成表格：

- `select`：有 fd 数量限制，且每次都要扫描
- `poll`：去掉了固定上限，但仍然需要线性扫描
- `epoll`：把“关注哪些 fd”和“哪些 fd 就绪了”拆开，减少无效遍历

epoll 真正的价值是：在大量连接中，更高效地知道“谁现在值得处理”。

### 慢请求为什么还是会拖垮服务

这类追问非常常见：

- epoll 只解决“就绪事件发现效率”
- 它不解决应用层处理慢
- 如果业务逻辑慢、线程池阻塞、下游响应慢，服务照样会抖

所以不能把 epoll 回答成高并发银弹。

### 零拷贝

零拷贝的本质不是“完全没有拷贝”，而是减少用户态和内核态之间不必要的数据搬运。

常见关键词：

- `sendfile`
- `mmap`
- DMA

你至少要能解释：

- 减少了哪些 copy
- 还有哪些开销没消失
- 为什么在大文件传输和静态资源分发里更有价值

## 高频问法

- epoll 为什么适合高并发？
- select / poll / epoll 最大差别是什么？
- 慢请求为什么仍然会拖垮 epoll 服务？
- 零拷贝减少了什么开销？
- sendfile 和 mmap 分别适合什么场景？

## 深挖与误区

- 不要把 epoll 说成“性能一定最好”，它只是在特定模型里更合适
- 不要把零拷贝理解成“完全零成本”
- 不要只讲内核机制，不讲业务线程池、请求处理和下游依赖
