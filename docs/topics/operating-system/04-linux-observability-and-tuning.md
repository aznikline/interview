# Linux 可观测性与性能排障

## 1 分钟速答

真正的 OS 工程感，不是知道多少术语，而是线上出问题时知道先看什么。Linux 可观测性题的核心是：`CPU`、`内存`、`I/O`、`网络`、`线程/进程` 这些维度怎么快速定位瓶颈。

## 核心机制

### CPU 视角

当服务“很慢”时，先分清：

- CPU 忙在用户态还是内核态
- 是单核打满还是多核平均高
- 是计算本身重还是锁竞争严重

常用工具：

- `top` / `htop`
- `ps`
- `perf`

### 内存视角

内存问题不只是 OOM：

- RSS 很高但并不一定泄漏
- page fault 多会拉高尾延迟
- swap 抖动会让服务严重退化

常用工具：

- `vmstat`
- `free`
- `sar`

### I/O 视角

很多慢服务不是 CPU 打满，而是卡在磁盘或网络 I/O：

- 磁盘队列长
- fsync 太频繁
- 下游响应慢
- 连接阻塞

常用工具：

- `iostat`
- `iotop`
- `strace`

### 网络与系统调用视角

当你怀疑系统调用或网络层有问题时：

- `strace` 能看到进程卡在哪类 syscall
- `ss` / `netstat` 看连接状态
- `lsof` 看文件和端口占用

这类工具的价值在于把“慢”拆成更具体的等待来源。

## 高频问法

- 线上 CPU 飙高你先看什么？
- 服务延迟抖动很大怎么排？
- 为什么 `strace` 能帮助定位慢请求？
- perf 能解决什么问题？
- RSS 高和内存泄漏是一回事吗？

## 深挖与误区

- 不要把排障题回答成工具清单背诵
- 不要说“先 top 一下”就结束，要继续说看什么指标
- 不要把所有慢请求都归因给代码，很多时候是 I/O、锁或系统调用等待
