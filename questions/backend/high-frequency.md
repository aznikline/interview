# 后端高频题

## 题目

MySQL 为什么使用 B+ 树作为通用索引结构？

## 一句话回答

B+ 树兼顾范围查询、磁盘局部性和稳定查询复杂度，比哈希更适合数据库通用场景。

## 展开回答

- B+ 树是多叉平衡树，高度低，磁盘 I/O 次数可控
- 非叶子节点只存索引键，叶子节点存记录指针或数据，扇出更高
- 叶子节点有序且可链表串联，天然支持范围查询和排序
- 哈希索引等值查询快，但无法高效支持范围查找和最左匹配

## 题目

Redis 为什么快？它快的边界在哪里？

## 一句话回答

Redis 快在于内存访问、单线程事件处理减少锁竞争以及高效数据结构，但它仍会受网络、慢命令、大 key 和持久化抖动影响。

## 展开回答

- 数据主要在内存中，避免磁盘随机 I/O
- 单线程执行命令路径短，避免多线程锁竞争
- 多路复用 + 事件循环处理大量连接
- SDS、跳表、压缩列表等结构针对典型场景优化
- 快的边界包括：大 key、复杂命令、阻塞操作、AOF 重写、网络带宽瓶颈

## 题目

缓存和数据库双写不一致怎么处理？

## 一句话回答

常见做法是以数据库为准，通过旁路缓存、延迟双删、异步订阅 binlog 或消息来降低不一致窗口。

## 展开回答

- 推荐模式是 Cache Aside：先更新 DB，再删除缓存
- 先删缓存再写库在并发下更容易出现脏读
- 延迟双删能缓解重建旧缓存的问题，但不是强一致
- 一致性要求更高时，用 binlog 订阅或 CDC 异步刷新缓存
- 真正要回答的是“不一致窗口多大、业务是否接受、成本多高”

## 题目

消息队列如何保证消息不丢？

## 一句话回答

消息不丢是生产者、Broker、消费者三段链路的联合保证，本质上是确认、持久化、重试和幂等。

## 展开回答

- 生产者侧：发送确认、失败重试、本地消息表
- Broker 侧：刷盘、副本同步、ISR / ack 策略
- 消费者侧：消费确认、重试队列、死信队列、幂等去重
- 面试里不要把“不丢”说成绝对保证，要明确是在什么故障模型下尽量保证
