# 后端核心题清单

## 题目

后端面试最应该优先刷哪些题，顺序应该怎么排？

## 一句话回答

先刷能串成完整工程链路的题：`MySQL -> Redis -> MQ -> 一致性 -> 高并发 -> 项目表达`。顺序上先抓主链路，再补追问，再补系统设计连接点。

## 展开回答

### 第一层：必须先拿下的 8 题

这 8 题是主链路，优先级最高：

- MySQL 为什么用 B+ 树？
- MVCC 解决了什么？为什么读写能并发？
- 索引失效有哪些典型场景？
- Redis 为什么快？边界在哪里？
- 缓存穿透、击穿、雪崩分别怎么治理？
- 更新数据库后为什么通常删缓存？
- MQ 如何保证消息不丢？
- 讲一个你做过的高并发或稳定性项目

如果这 8 题讲不顺，后面的追问很难接住。

### 第二层：必须能接住的追问

- redo log、undo log、binlog 的区别
- 可重复读为什么还能防幻读
- 行锁、间隙锁、next-key lock 的区别
- 热 key、大 key、慢查询、消息积压怎么排查
- 至少一次为什么一定会带来重复消费
- 幂等在业务里到底怎么落地

### 第三层：要能连到系统设计的题

- 分布式锁为什么经常不是最优解
- 如何设计秒杀/下单链路
- 如何做限流、熔断、降级
- 一致性为什么没有银弹
- 时钟回拨为什么会影响分布式 ID

### 建议刷题顺序

1. 先看 [后端专题首页](../../docs/topics/backend/00-index.md)
2. 再看 MySQL、Redis、MQ 三篇专题
3. 再刷 [后端高频题](high-frequency.md)
4. 再刷 [后端进阶题](distributed-and-db.md)
5. 最后做 1 次 mock，把这些题串成链路

### 每题最低输出标准

每道题至少要能说出：

- 一个 `1 分钟回答`
- 两个 `追问`
- 一个 `工程案例`
- 一个 `边界或反例`

### 1 分钟速答表

| 题目 | 最低合格回答 |
| --- | --- |
| MySQL 为什么用 B+ 树？ | 因为磁盘页访问贵，B+ 树更矮、范围查询更稳、叶子节点顺序更适合扫描。 |
| MVCC 解决了什么？ | 它让普通读能基于版本快照减少和写操作的锁冲突，但更新和当前读仍要加锁。 |
| 索引为什么会失效？ | 本质上是查询条件没法稳定利用有序性，比如最左前缀被破坏、函数计算、范围后继续过滤。 |
| Redis 为什么快？ | 内存访问快、数据结构针对高频场景优化、单线程事件模型减少竞争，但大 key 和慢命令仍会拖垮延迟。 |
| 缓存穿透、击穿、雪崩怎么区分？ | 穿透是查不存在，击穿是热点失效，雪崩是大量 key 同时失效；三者治理点分别是校验、保护热点、错峰与兜底。 |
| 为什么通常删缓存而不是更新缓存？ | 因为数据库是真源，删缓存更稳、更简单，也更不容易在并发下把旧值覆盖回去。 |
| MQ 如何保证消息不丢？ | 生产端确认、Broker 持久化、消费端 ack 和重试链路都要覆盖，否则只能做到局部不丢。 |
| 高并发项目该怎么讲？ | 先讲目标和约束，再讲瓶颈、方案、指标收益和失败场景，不要只列组件名。 |
| 分布式锁为什么经常不是最优解？ | 因为它把问题转成了锁服务正确性问题，很多场景用幂等、唯一约束、状态机更稳。 |
| 一致性为什么没有银弹？ | 因为一致性、可用性、延迟、侵入成本之间一定要取舍，关键是先说清业务能接受什么。 |

### 最小合格回答标准

如果你只能保住后端一面的及格线，至少做到：

- 每题先给结论，不绕背景
- 能补一个失败场景，比如缓存删除失败、MQ 重复消费、锁误删
- 能把题目连回一个真实链路，比如下单、库存、通知、Feed
- 被追问时不空转，至少能继续讲 `代价 / 边界 / 监控指标`

## 面试官追问

- 如果只给你 30 分钟准备，你先保哪 5 题？
- 如果项目不强，怎么靠这些题稳住一面？
- 哪些题最适合连到系统设计？
- 哪些题最容易被问到故障处理？

## 易错点

- 只会背组件，不会讲链路
- 只会讲 happy path，不会讲故障与补偿
- 只会说“项目很复杂”，却说不出指标和取舍
