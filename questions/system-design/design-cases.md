# 系统设计进阶题

## 题目

设计 Feed 流时，为什么要在 fanout on write 和 fanout on read 之间取舍？

## 一句话回答

因为前者写扩散重、读延迟低，后者写轻、读聚合复杂；普通用户和大 V 的流量模式不同，往往需要混合策略。

## 展开回答

- 写扩散模式适合关注数多、粉丝数少的普通用户
- 读扩散模式适合大 V，避免一次发帖扇出到海量粉丝
- 混合模式按账号级别或内容类型路由
- 需要配套缓存、补偿重建和删除同步策略

- 时间线删除和屏蔽如何传播？

## 题目

为什么系统设计题里容量估算不能省略？

## 一句话回答

因为没有容量估算，你无法判断单机是否足够、缓存是否必要、分片是否要做，也无法解释瓶颈和成本。

## 展开回答

- QPS 决定接入层和服务层压力
- 数据量决定存储选型与分片策略
- 带宽与对象大小决定 CDN、压缩和传输成本
- 估算不必极精确，但必须能支撑架构选择

- 面试时怎么算才不会太慢？

## 题目

如何设计一个全局唯一 ID 系统？

## 一句话回答

全局 ID 设计要在唯一性、有序性、可扩展性和可用性之间取舍，常见方案包括数据库自增、号段、Snowflake 和 UUID。

## 展开回答

- UUID 简单但无序且长
- 数据库自增简单但中心化
- 号段模式兼顾性能与简单性
- Snowflake 适合分布式生成，但依赖时钟与节点管理

- 强有序和近似有序有什么差别？
- 为什么很多业务更偏号段？

## 题目

设计一个搜索建议系统时，核心难点是什么？

## 一句话回答

核心难点在于低延迟前缀匹配、热点词更新、多语言处理和个性化排序，这决定了它不仅是 Trie 结构问题，更是索引和在线服务问题。

## 展开回答

- 前缀索引要支持高频读
- 热门词和个性化结果要分层处理
- 更新链路要兼顾实时性与成本
- 在线服务还要做限流和降级

- 个性化和全局热门怎么混排？
- 如何处理脏词和风险词？
